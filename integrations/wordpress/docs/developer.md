# Developer API, tests and release

Runtime code is self-contained PHP. `Config`, `Http`, `Oidc` and `TokenValidator` isolate the provider/versioned identity contract. `Store` owns migrations/mappings/one-use state/audit; `Sessions` owns local-session association and backchannel invalidation; `Controller` owns browser flow, `Surfaces` supported UI hooks, `Admin` migration settings, and `Emergency` host recovery.

Theme/editor entry points: `[accesslobby_login]`, `[accesslobby_login intent="join"]`, `[accesslobby_account]`, block `accesslobby/login`, `accesslobby_login_url($safe_destination, $intent)`, `accesslobby_logout_url()`, actions `accesslobby_login` and `accesslobby_account_actions`. `accesslobby_authenticated($local_user_id, $provenance)` announces completion but grants no capability. `accesslobby_audit($safe_event)` is the structured operational hook. Custom membership applications use the standard WP session and their own entitlement checks; arbitrary plugins are not certified automatically.

Core hooks insert SSO in wp-login/registration/wp_login_form. Woo hooks insert in login/registration and account dashboard. The frontend adapter discovers conventional WordPress/Woo login forms, including dynamically shown modals, without theme-source edits. It relies on observable supported form fields; custom WoodMart account-builder/modern Woo/membership variants require actual tests.

Known Woo account/connector shortcode/block pages send private/no-store headers. For a custom membership/account route, return true from `accesslobby_is_auth_surface($known)` when the current route contains dynamic account state. Server/CDN cache exclusions remain required independently. Profile links use native external form association, preserving the WordPress profile form.

Enforced mode accepts browser cookie issuance only inside the connector's validated session or host recovery flow. Custom frontends should redirect through `accesslobby_login_url()`, not authenticate a local password and call `wp_set_auth_cookie()` themselves. The guard preserves cookie clearing; it also preserves Application Password API authentication according to the machine setting. Arbitrary PHP replacing core authentication or writing raw cookies remains outside a certified adapter boundary. Woo/Core anonymous registration is guarded separately so an unchecked local checkout-account flow cannot create a competing identity path. Guest/signup database options are not rewritten.

`composer install --no-interaction` installs locked development tooling. `python3 scripts/prefix-jwt.py` applies a namespace-only transformation to the locked maintained JWT library. Commit its provenance and license. Run PHPUnit, PHPStan and PHPCS plus syntax/security audit; CI repeats the package transformation and detects drift. The packaging script includes runtime/docs/license only and builds a deterministic normal plugin ZIP.

`scripts/qualify.py` runs real WordPress/MariaDB, actual HTTPS Keycloak, unchanged AccessLobby API source/PostgreSQL and two independently registered installations (root and `/gh/`). The workflow is the reproducible runtime/dependency setup. `tests/integration.php` tests local identity/commerce/session behavior, `security-integration.php` adversarial hooks/audit/recovery/schema behavior, `concurrency.py` separate-process JIT/link/state races, `browser.mjs` actual Chromium journeys, and `http_flow.py` explicit HTTP protocol acceptance when a local browser cannot launch. HTTP evidence is never substituted for browser results. `ALWP_WITH_WOO=false` qualifies plain WordPress independently; current Woo11.3 requires WP7.0+.

Run only in a fresh throwaway environment with `ALWP_DISPOSABLE_FIXTURE=1`, loopback MariaDB/PostgreSQL, and the official runtime downloads specified by `.github/workflows/wordpress.yml`. The command is `python3 integrations/wordpress/scripts/qualify.py --runtime RUNTIME_DIRECTORY --package INSTALLABLE_ZIP --keycloak-home DISPOSABLE_KEYCLOAK_HOME`. It recreates the named fixture databases and seeds synthetic reviewed clients. Never point it at a developer's durable IAM/database directory. It refuses non-loopback databases or absent explicit fixture authorization. Native local processes can be supplied by the `ALWP_MARIADBD`, `ALWP_NATIVE_USR`, `ALWP_INITDB`, `ALWP_POSTGRES`, `ALWP_PSQL`, `ALWP_PHP` and `JAVA_HOME` environment paths. Optional `ALWP_FIXTURE_DRIVER=http` selects protocol-only coverage.

Verification email is captured by an isolated loopback SMTP sink; no message is delivered externally. Passwords, realm imports, keys and raw verification links stay in private disposable directories. CI uploads only categorical JSON reports, never the raw runtime directory or private logs. Normal ZIP installation/deactivation/reactivation, schema upgrade, uninstall and reinstall/data preservation run on both sites. Synthetic registry review/DNS rows do not qualify real publisher/domain onboarding. Exact results live in `docs/qa/wordpress-codex-2026-11-23` at repository root; the compatibility matrix distinguishes fixture, estate and external gates.

Source/CI/runtime/pilot/production are separate evidence dimensions. Keep pilot versioning until the vertical slice, security review, actual two-site quiet SSO/logout, preserved Woo customer history and safe rollback pass. Merge through protected-main PRs; publish immutable versioned ZIP/hash and exact source revision only after required checks. No external publisher activation belongs in this first-party release.
