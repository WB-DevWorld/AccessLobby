# AccessLobby WordPress connector contract v0.1

Status: MVP-PROVISIONAL, first-party pilot; 2026-11-23. Owner instructions establish both modes, local data ownership, explicit linking and logout choice. This does not activate external publishers.

Each independent installation/environment has an exact issuer, distinct reviewed client and exact callback, signed-out and backchannel URLs. URLs derive from WordPress `site_url()`; destinations derive from `home_url()` and must remain on the installation's origin and allowed path. Code + mandatory PKCE S256/state/nonce, RS256/JWKS verification and `/v1/me` precede any local account. The existing public-client profile is supported; a confidential secret can only be supplied outside options through a constant. Secrets/tokens are never rendered or logged. Protocol and identity resolution are separate classes.

The first-party identity adapter validates both tokens, calls `/v1/me` and `/v1/application-entry`, checks versioned responses and active person, then resolves a unique local mapping. Person identity, app entry, WP role, commerce and membership entitlements are distinct. Registry admission is mandatory for this connector. No organization endpoint is called and no role claim is interpreted.

Per-installation InnoDB tables uniquely constrain `(issuer, durable identity)`, `(issuer, subject)` and local user ID through indexed hashes; original values are retained for collision checks. Email is a profile attribute only. Within the same pinned issuer, a verified changed subject resolving to the same person updates the subject mapping with an audit event. A changed issuer/client requires controlled migration, never an inferred email link. Existing maps are not repointed automatically. Replacing IAM requires AccessLobby to preserve its durable resolution contract first.

New-user JIT is disabled until explicitly configured. Only subscriber/customer roles whose actual capabilities are safe are accepted. Verified email is required for first-party JIT; an email collision returns a linking-required error, creates nothing and does not attach an existing user. A customer role is an explicit local setting, never inferred from global claims. Account creation follows identity and admission validation. Existing users keep IDs, roles, profiles, orders and metadata unchanged.

Existing users POST Connect AccessLobby with a WP nonce from their own authenticated account. The five-minute OIDC flow records the local user and current session fingerprint and requests fresh IAM authentication. The callback revalidates that exact still-active local session, fresh `auth_time`, both OIDC proofs, admission and mapping uniqueness. Success rotates the current WordPress token and associates the replacement with the IAM `sid` immediately; unrelated device sessions remain. Links and conflicts are audited. No administrative email shortcut exists. Unlinking requires fresh dual proof in hybrid mode; enforced-mode recovery requires host administration. Retained inactive links prevent silent identity reuse.

`WordPress + AccessLobby` retains ordinary local authentication and adds supported core/WooCommerce hooks, shortcode, block and public helper API. `AccessLobby only` redirects normal interactive core login/recovery/registration, protected login redirects and unauthenticated My Account; supported frontend forms initiate SSO when opened/submitted. Checkout remains anonymous when WooCommerce permits it. Membership adapters must explicitly use the helper API; arbitrary custom authentication code is not certified.

Enforced mode also guards WordPress `send_auth_cookies`: only the validated connector session factory and verified host recovery can issue new browser cookies; clearing cookies is always permitted. This covers conventional custom frontends that directly call WordPress cookie APIs. It does not sandbox arbitrary trusted PHP that replaces core pluggable functions or writes raw headers. Existing cookie-based REST requests and Application Password API authentication retain their separate policies.

WooCommerce local checkout registration is suppressed in enforced mode without changing stored guest/signup options. Optional shoppers can continue as guests or begin AccessLobby Join. Account-required checkout automatically starts SSO and returns to checkout. Core/Woo anonymous registration hooks and forged classic checkout account-creation submissions fail closed; anonymous Store API customer creation also reaches the Woo registration guard. Authenticated administrative creation and host/background operations remain local responsibilities. Modern checkout/account UI still requires its own compatibility qualification.

Enforced mode requires HTTPS, a recent connection check, an authenticated linked administrator, host recovery configured, a recorded backup/rollback reference and explicit acknowledgement of remaining unlinked users. Existing privileged accounts must be linked or individually acknowledged through the migration gate. New local password authentication fails closed during outage. Existing sessions follow their expiry; enforced enablement invalidates existing local sessions deliberately after the operator's acknowledged migration step. Application Passwords/XML-RPC/REST/WP-CLI/cron follow an explicit machine policy, separate from human login.

Emergency recovery is a host-enabled, exact-remote-IP-restricted, short-lived one-use WP-CLI ticket for an existing administrator. No outage exposes a password form. The emergency token is POSTed, never put in a URL; its hash is stored, use is audited, and the resulting session lasts at most 15 minutes. Proxy headers do not establish the allowlisted IP. Normal recovery is host CLI deactivation/rollback with a recorded reason.

Every supported logout entry opens a nonce-protected choice. Site-only destroys only the current local session and leaves IAM/other sites active. All-connected-apps also initiates issuer logout using `client_id`, an exact registered signed-out URL and state; no ID token is placed in the URL. The issuer may ask for confirmation. A signed-out landing route never automatically signs the person back in. All-apps is not all-devices.

Backchannel accepts only signed RS256 tokens from the pinned issuer/JWKS, intended audience, fresh `iat`, optional valid `exp`, one exact event object, nonempty `sid`/`jti` and no `nonce`. Durable replay claims and revoked-sid tombstones serialize against login. Only associated WP session tokens are destroyed; their recoverable values are encrypted with WP salts. Other local/device sessions are untouched. Peers unavailable during notification can retain sessions until the one-hour cap; reliable delivery/reconciliation remains a production acceptance gate.

Authentication/control routes send private no-store/referrer/noindex headers and declare WordPress cache exclusions. CDN/server exclusions are required independently. No tokens persist in browser storage; code travels only in the standard callback query and must be redacted at proxy level. Transient flow/session payloads are encrypted and expire; audit stores only event classes, local numeric IDs and correlation IDs.

Network multisite activation and multisite account semantics are explicitly unsupported in this increment; separate root/subdirectory installations are the qualification target. External profile selection fails closed until token-wide privacy, internal person continuity, separate API audience, consent, publisher proof, lifecycle and independent pilot are implemented. Installing this first-party package is not external onboarding approval.
