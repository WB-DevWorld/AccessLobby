## Host preparation checkpoint

1. Attach a Hetzner Cloud Firewall: allow SSH from the operator's verified current IP, and 80/443 from intended clients. Do not expose Dokploy port 3000, databases, Keycloak management port 9000 or application ports. Maintain the current SSH session while proving a second connection works. A host firewall can supplement the provider firewall; Docker-published ports require special care.
2. Verify the server is still empty and review current OS security updates. Install a pinned, supported Dokploy release following the official installer guidance. Dokploy owns 80/443 and host port 3000. Use a private administrative path (for example an SSH tunnel to localhost:3000) for initial setup, then HTTPS and restricted access. Do not open the panel publicly to make setup easier.
3. Create DNS records and TLS for distinct **staging** origins. Proposed names: `accesslobby.realjanelove.com` (web), `iam.accesslobby.realjanelove.com` (OIDC issuer host), and `api.accesslobby.realjanelove.com` (identity API). The exact names and certificates must be verified before rendering the realm or registering callback URIs. Keep production on a separate HTTPS issuer and separate secrets, databases, volumes, deployment and test users. A shared host remains a shared failure domain.
4. The owner reports an OVHcloud S3-compatible bucket `devbackups` in `rbx`; screenshots show versioning, SSE-OMK and an uploaded Dokploy control-plane backup object. Dokploy shows a daily UTC backup with retention 30. Confirm private bucket access policy and perform an isolated restore drill. Back up both product PostgreSQL databases independently after deployment; the Dokploy archive does not include them.

## Deploy the qualified artifacts

1. After main is protected and the PR qualifies, record the merged commit and the API/web `sha256` digests from the main image workflow. Give Dokploy scoped GHCR pull credentials if the packages are private. Build images in CI, not on the server.
2. Use one Dokploy **Docker Compose** service with the repository-root `compose.dokploy.yaml` (Compose Path `./compose.dokploy.yaml`). It has no host port publications, uses private database networking, and gates API startup on the one-shot schema migration. The root location makes `../files` resolve to Dokploy's persistent sibling mount directory. Create a separate service/project for production later. Review Dokploy's **Preview Compose** before deployment; confirm the `iam`, `api`, and `web` services join the proxy network while neither database nor the migration service has an external route.
3. Render the initial realm with the staging `WEB_BASE_URL`, review it, and place the rendered file in Dokploy's persistent `../files/keycloak-import` mount. Only the sanitized realm belongs there. Git auto-deploy replaces the checkout directory, so do not mount generated state from inside the cloned repository. Later Keycloak changes require an explicit reconciled configuration step; initial realm import does not update an existing realm.
4. Supply distinct staging secrets through the protected Dokploy environment: `IAM_DB_PASSWORD`, `IDENTITY_DB_PASSWORD`, `IAM_ADMIN_USERNAME`, `IAM_ADMIN_PASSWORD`, `IAM_PUBLIC_ORIGIN`, `OIDC_ISSUER`, `WEB_BASE_URL`, `ALLOWED_CLIENT_IDS`, `SESSION_SECRET`, `API_IMAGE`, `WEB_IMAGE`, and `GIT_SHA`. The OIDC issuer must be the exact externally reachable HTTPS value, including `/realms/accesslobby-first-party`. Use digest references for both images; do not use mutable `latest` tags. Because the Compose file interpolates `IDENTITY_DB_PASSWORD` directly into a PostgreSQL URI, generate DB passwords from URL-safe hexadecimal bytes (for example `openssl rand -hex 32`) until the connection configuration is revised; do not use URI punctuation unescaped. `SESSION_SECRET` is 32 random bytes encoded as base64url.
5. Route `api` to container port 3001 and `web` to container port 3000 over HTTPS in the Compose service Domains tab. The public IAM host requires an ingress rule that forwards only the necessary Keycloak OIDC paths (`/realms/accesslobby-first-party/`, `/resources/`, and required `/.well-known/` paths) to port 8080. Do **not** add a generic host-only IAM domain route: it would also expose `/admin/` and `/realms/master/`. Keep the admin paths accessible only over an operator-restricted route, never proxy management port 9000, and validate that forwarded headers cannot be spoofed. Preview the final Traefik rules and test both allowed OIDC paths and rejected public admin/master paths before accepting staging. This is an implementation gate, not yet configured in Dokploy.
6. Deploy the independent reference consumer with its own exact HTTPS callback and logout URIs. Run the full browser login, repeat mapping, local authorization denial, logout/re-entry and negative token/redirect matrix. Record SHA, digests, migration, health, backups and restore evidence. Enable automatic staging promotion only after this first deployment and its recovery path work; production requires a separate Go/No-Go.

## Migration to another server

Install the same Compose configuration and qualified images on the new host, restore the two databases and Dokploy configuration from off-host backups, provision environment secrets, verify login on the new host, then change DNS. Preserve the **production issuer URL** across the move. Rehearse rollback and estimate the identity-service interruption before changing production traffic. Container images alone do not contain durable identities.
