## Host preparation checkpoint

1. Attach a Hetzner Cloud Firewall: allow SSH from the operator's verified current IP, and 80/443 from intended clients. Do not expose Dokploy port 3000, databases, Keycloak management port 9000 or application ports. Maintain the current SSH session while proving a second connection works. A host firewall can supplement the provider firewall; Docker-published ports require special care.
2. Verify the server is still empty and review current OS security updates. Install a pinned, supported Dokploy release following the official installer guidance. Dokploy owns 80/443 and host port 3000. Use a private administrative path (for example an SSH tunnel to localhost:3000) for initial setup, then HTTPS and restricted access. Do not open the panel publicly to make setup easier.
3. Create DNS records and TLS for distinct **staging** origins. Proposed names: `accesslobby.realjanelove.com` (web), `iam.accesslobby.realjanelove.com` (OIDC issuer host), and `api.accesslobby.realjanelove.com` (identity API). The exact names and certificates must be verified before rendering the realm or registering callback URIs. Keep production on a separate HTTPS issuer and separate secrets, databases, volumes, deployment and test users. A shared host remains a shared failure domain.
4. The owner reports an OVHcloud S3-compatible bucket `devbackups` in `rbx`; screenshots show versioning, SSE-OMK and an uploaded Dokploy control-plane backup object. Dokploy shows a daily UTC backup with retention 30. Confirm private bucket/object ACLs and scoped user access, then perform an isolated restore drill. OVHcloud Object Storage currently does not provide bucket policies; use ACLs and user policies. Because versioning is enabled, Dokploy's `Keep Latest: 30` does not itself guarantee permanent storage cleanup: a delete may leave a noncurrent object version and a delete marker. Define an OVHcloud lifecycle rule scoped to the Dokploy backup prefix, with a deliberate noncurrent-version expiration and enough recovery history, then test retention without affecting other bucket users. Back up both product PostgreSQL databases independently after deployment; the Dokploy archive does not include them.

## Deploy the qualified artifacts

1. Record the qualified main commit and API, web and IAM gateway `sha256` digests from the main image workflow. Image publication is triggered only by successful **push-to-main CI**, and must use that CI run's exact head SHA. Confirm the publication run succeeded before entering any digest into Dokploy. Give Dokploy scoped GHCR pull credentials if the packages are private. Build images in CI, not on the server. The owner deployed the matching three digests from main `99c9148` on 2026-09-25; the separate consumer image was published from main `640f105` and deployed in its own Dokploy Compose service by owner report.
2. Use one Dokploy **Docker Compose** service with the repository-root `compose.dokploy.yaml` (Compose Path `./compose.dokploy.yaml`). Leave the deprecated **Enable Isolated Deployment** switch **off**. The source Compose has no host port publications and defines two internal networks: `backend` for databases, migration, API, web and IAM; `iam-edge` shared only by IAM and the gateway. In Dokploy's **Networks** section, leave each per-service network selection empty and each **Detach dokploy-network** switch off: Dokploy adds its shared network only to the three domain targets (`iam-gateway`, `api`, `web`). Never add a domain for `iam`, either database or `migrate`. The root location makes `../files` resolve to Dokploy's persistent sibling mount directory. Create a separate service/project for production later. Review **Preview Compose** before deployment: only `iam-gateway`, `api` and `web` may join `dokploy-network`; `iam` must have only `backend` and `iam-edge`; databases and migration must have only `backend`. Confirm no host ports and no domain labels on private services. If preview differs, stop before deployment.
3. Render the initial realm with the staging `WEB_BASE_URL`, review it, and place the rendered file in Dokploy's persistent `../files/keycloak-import` mount. Only the sanitized realm belongs there. Git auto-deploy replaces the checkout directory, so do not mount generated state from inside the cloned repository. Later Keycloak changes require an explicit reconciled configuration step; initial realm import does not update an existing realm.
4. Supply distinct staging secrets through the protected Dokploy environment: `IAM_DB_PASSWORD`, `IDENTITY_DB_PASSWORD`, `IAM_ADMIN_USERNAME`, `IAM_ADMIN_PASSWORD`, `IAM_PUBLIC_ORIGIN`, `OIDC_ISSUER`, `WEB_BASE_URL`, `ALLOWED_CLIENT_IDS`, `SESSION_SECRET`, `API_IMAGE`, `WEB_IMAGE`, `IAM_GATEWAY_IMAGE`, and `GIT_SHA`. The OIDC issuer must be the exact externally reachable HTTPS value, including `/realms/accesslobby-first-party`. Use digest references for all three custom images; do not use mutable `latest` tags. Because the Compose file interpolates `IDENTITY_DB_PASSWORD` directly into a PostgreSQL URI, generate DB passwords from URL-safe hexadecimal bytes (for example `openssl rand -hex 32`) until the connection configuration is revised; do not use URI punctuation unescaped. `SESSION_SECRET` is 32 random bytes encoded as base64url.
5. Route `api` to container port 3001 and `web` to container port 3000 over HTTPS in the Compose service Domains tab. Add one HTTPS host-only domain `iam.accesslobby.realjanelove.com` targeting **`iam-gateway`**, container port `8080`, Path `/`, Strip Path off. The gateway allows only `/realms/accesslobby-first-party/` and `/resources/`; other paths return 404 even when a peer on the proxy network addresses the gateway directly. Never target the `iam` service in Domains. A root `/.well-known/` route is not needed for the v0.1 realm-specific discovery contract; add it only after a specific reviewed gateway change if a real client requires the RFC 8414 path. Keep admin access over an operator-restricted path or container-side CLI, never proxy management port 9000. The owner observed 404 for restricted public paths and unchanged discovery issuer/endpoints with forged forwarding headers on 2026-09-25.
6. Deploy the independent reference consumer using the [separate staging runbook](reference-consumer-staging.md). Run its browser login, repeat mapping, local authorization denial, logout/re-entry and negative token/redirect matrix. Record SHA, digests, migration, health, backups and restore evidence. Enable automatic staging promotion only after this first deployment and its recovery path work; production requires a separate Go/No-Go.

## Migration to another server

Install the same Compose configuration and qualified images on the new host, restore the two databases and Dokploy configuration from off-host backups, provision environment secrets, verify login on the new host, then change DNS. Preserve the **production issuer URL** across the move. Rehearse rollback and estimate the identity-service interruption before changing production traffic. Container images alone do not contain durable identities.
