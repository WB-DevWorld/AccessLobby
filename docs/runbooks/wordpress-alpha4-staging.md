# Controlled alpha.4 staging adoption

This runbook is prepared for the executor that reaches the approved estate hosts. It is not an installation record or production authorization. Keep Cursor PR60 and Codex PR61 separate until comparison/selection; do not overwrite another lane's client, plugin or evidence.

The tested implementation is `7c9ec8c8985939addb17ccf1e25bd8313c652eb3`; plugin 0.1.0-alpha.4 ZIP SHA256 is `906f904449dc23a1d5bfaeab07c77365bd09c5cdf57a094a00676cb2d33cb4f5`. Verify the bytes before use. Do not install from a moving branch or assume an evidence commit changed the package. See the alpha.4 acceptance and retained CI for qualification boundaries.

1. Run the private read-only estate inventory under the established site Unix owner. Record actual home/site URLs, PHP/WP/Woo/theme/plugins, HPOS, guest policy, local roles, existing auth integrations and proxy/cache topology. A reported version from the other lane is a lead; the live inventory is authoritative. Do not dump credentials or customer/order content into Git.
2. After candidate selection, follow protected-main PR/CI/immutable-image staging procedures. Record the exact resulting source/image digests. Apply additive API migrations005–007 before the API revision, then verify readiness and existing AccessLobby web/PWA/account/logout behavior. No realm re-import, IAM-table access or external activation is part of this rollout. Leave EXTERNAL_PROFILE_PREVIEW_ENABLED unset/false. A pre-merge comparison uses disposable fixtures, not a bypass of protected deployment governance.
3. Establish a private site backup and demonstrated restore/rollback reference. Use training/staging first. Install the verified ZIP in hybrid mode. Copy exact callback, signed-out and backchannel routes from its settings; do not assume wp-login.php is at the domain root. In AccessLobby developer tools select WordPress, request a distinct client, prove the shown DNS record, record first-party review, run private provisioning/readback and choose explicit authenticated_open or grant_required admission.
4. Preserve existing guest/account-required policy. Configure JIT only with a reviewed safe subscriber/customer default when wanted. Existing staff/customer accounts must prove local control and fresh AccessLobby authentication in the bounded link flow. No matching-email or operator-written mapping shortcut is permitted. Compare local numeric user/order owner, roles/capabilities, addresses/history and installed domain entitlements before/after without changing them.
5. Verify connection metadata and opaque receipt availability; establish fresh sessions. Exercise core/admin/frontend/My Account, actual WoodMart/Kadence/mobile forms, return targets, denied local resources, both logout scopes and another independent site/client. Include a separate browser device, missed peer backchannel, status outage/grace/recovery, required-account checkout and the site's own guest policy. Verify actual cache/CDN/auth route exclusions, no-store and authorization-log redaction. Metadata success or a version-matched public fixture alone is not a site pass.
6. Configure/rehearse host recovery before enforced mode: explicit host enablement, exact trusted remote IP and one-use ticket for an existing administrator, secret kept only in the private operator/browser session. Do not trust arbitrary forwarded IP headers. Record readiness counts, privileged/unlinked acknowledgements and backup/rollback references. Enable enforced mode only through its authenticated readiness gate; test outage and rollback without reopening a public local-password route.
7. Retain a per-site record with environment, observed stack, source/image/ZIP hashes, client/registered routes, mode/login/link/JIT/logout/SSO/commerce/guest results, emergency/restore proof and real blockers. Report SUPPORTED/QUALIFIED/PARTIALLY QUALIFIED/UNTESTED/UNSUPPORTED/BLOCKED precisely. Keep raw credentials, token-bearing logs, verification links and customer exports private.

Rollback retains all additive API tables, WordPress users, links and Woo data. Use the previous qualified ZIP and recorded host recovery/deactivation procedure as appropriate. Normal WordPress web upgrades manage their PHP cache context; a CLI-driven downgrade can require the established PHP-FPM/opcode-cache reload procedure and HTTP version readback. Do not declare success from a ZIP header while the web runtime serves an older bootstrap. Replay/legacy receipt limits remain as documented in the plugin logout guide.

External prepared profiles are deliberately inactive. Do not reclassify one as first party to bypass the privacy gate, and do not call an isolated pairwise token probe an external WordPress pilot.
