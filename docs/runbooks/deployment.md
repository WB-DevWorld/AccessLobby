# Staging and production deployment

**Prepared procedure; not evidence of deployment.** Use separate hosts or strictly isolated environments, databases, credentials, issuer URLs, proxy routes and backup storage.

1. Verify DNS/TLS ownership, Docker host and trusted reverse proxy. The proxy terminates HTTPS and the IAM gateway overwrites untrusted forwarded headers before Keycloak. The Dokploy Compose publishes no host app or database ports; only the IAM gateway, API and web receive proxy domains. Restrict Keycloak `/admin` and management port to operators. Verify issuer discovery returns the exact external HTTPS URL.
2. Create environment-specific secrets out of Git, including unique database passwords, bootstrap admin credentials, 32-byte web session key and protected SMTP credentials. The initial pinned baseline is Keycloak 26.7.4 and PostgreSQL 17.11; confirm current patch support before promotion. Set `WEB_BASE_URL`, `API_PUBLIC_ORIGIN`, `IAM_PUBLIC_ORIGIN`, `OIDC_ISSUER`, `ALLOWED_CLIENT_IDS`, `GIT_SHA` and qualified `IAM_IMAGE`/`API_IMAGE`/`WEB_IMAGE`/`IAM_GATEWAY_IMAGE` digests. The separate reference-consumer service needs its own `CONSUMER_IMAGE` digest. `iam` and `iam-config` both require `IAM_IMAGE`; missing it prevents Compose interpolation before containers start.
3. Render realm config for a **new** environment with `WEB_BASE_URL=... API_PUBLIC_ORIGIN=... python3 infra/scripts/render-realm.py`. The import is create-only; the `iam-config` job reconciles the existing realm's theme and registration/recovery flags. Later client/backchannel changes still need an approved Keycloak admin update. Test SMTP and email verification before inviting users. No secret or user data belongs in the template.
4. The main-branch publish workflow prepares GHCR images tagged by commit and records immutable digests. The last publicly observed staging baseline from `4debd6e` is in the [branded cutover runbook](auth-theme-staging-cutover-2026-09-28.md); the published `2d35213d` account-context candidate and five matching pins are in the [new handoff](account-contexts-staging-2026-09-29.md). Qualify each later release separately. Use the exact qualified digests for staging and production. Start the isolated databases and IAM, then run `docker compose --env-file <staging-env> -f infra/compose.production.yaml run --rm --no-deps api node dist/migrate.js` with the same versioned image. Start API/web only after migration. Do not send traffic to a non-migrated API.
5. Register a separately deployed compatible consumer using the [onboarding process](../consumer-onboarding.md). Check OIDC discovery/JWKS issuer, `/health/live`, `/health/ready`, a controlled login, `/v1/me`, repeat login, logout/re-entry, bad token/issuer/audience rejection and consumer local denial. Record SHA, image digests, versions, migration and logs without tokens. The read-only [runtime inspection command](auth-theme-staging-cutover-2026-09-28.md#prepared-bulk-evidence-pass) checks the actual Compose containers against the qualified digest manifest without reading environment variables. Execute backup and restore drill in an isolated environment.
6. Present Go/No-Go evidence for production approval. Promote the exact image digests, with production secrets/realm/callbacks, migrate then smoke. Observe errors and login failures. Roll back images to previous digests only if schema remains compatible; otherwise use the documented forward fix or a verified database restore with explicit data-loss assessment.

Do not claim CI/CD staging promotion until host and registry automation are connected. Qualify a controlled production cohort using a separately deployed compatible consumer; report named peer adoption as a separate milestone.
