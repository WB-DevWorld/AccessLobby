# First-party app onboarding: controlled staging pass

This is the ordered acceptance pass for merged PR #42, pinned source `aadfad381b3f43d8c93cce1ba84805aead4efb52`, tracked by issue #44. Use the [published-image handoff](app-onboarding-staging-handoff-2026-09-29.md); current public staging still reports the older account-routing source. Use an owned staging hostname and a disposable first-party test peer; external publishers are out of scope until their identifier and consent contract exists. This runbook does not authorize production promotion. Record only app UUIDs, client IDs, status codes, commit and image digests in a private evidence log; never record tokens, DNS control credentials or personal data.

1. **Establish the baseline.** Record the running web/API/IAM digests and API source SHA. Back up and restore-check the identity database according to the existing staging procedure. Confirm the new API image and migration 004 are approved together. Roll out the migration before the API and web images; confirm readiness and existing pilot sign-in after deployment. Do not enable `APP_ENTRY_REQUIRED` for the legacy reference consumer yet.
2. **Request without IAM mutation.** From a first-party account, request a disposable client in `/apps` with exact HTTPS callback/logout URLs, optional implemented backchannel endpoint, and `authenticated_open`. Confirm `requested/unreviewed`, a unique DNS TXT challenge, no new Keycloak client and `403 application_unavailable` on a token for that client if one already exists. Confirm a second person cannot see the owner's request or verify its hostname.
3. **Prove hostname control.** Publish the exact TXT value at the shown `_accesslobby-verify.<callback-hostname>`. Verify it in `/apps`. A missing or altered value must yield `409 origin_proof_missing`; a DNS outage yields 503. Record the verified state and remove the record temporarily before activation to confirm that the private runner refuses stale proof, then restore it. DNS proof alone does not classify a publisher as first party.
4. **Review and activate.** Independently confirm the publisher, approved entry policy, exact callback/logout/backchannel endpoints, and first-party classification. Keep the review reference and scoped IAM token in the protected operator workflow. Run `node dist/provision-app.js <app-uuid> --plan`, compare the representation, then `node dist/provision-app.js <app-uuid> --activate-first-party <review-reference>` from a private runner with database and internal IAM access. Read back the client in Keycloak: exact redirect, logout, optional backchannel with session required, PKCE S256, API audience, public code flow; verify one client and one active registry row. A mismatched preexisting client must leave the registry inactive. No realm should be created.
5. **Exercise open entry without a person list.** Deploy a second, isolated instance of `compose.consumer.dokploy.yaml` on the approved callback hostname, using the qualified reference-consumer image, the activated client ID in `OIDC_CLIENT_ID`, its exact `CONSUMER_ORIGIN`, and `APP_ENTRY_REQUIRED=true`. Keep the existing `reference-consumer` project on its default client ID with entry checking off; never switch that pilot project to the disposable client. Sign in two distinct active people to the isolated peer. Both should receive a 200 self-scoped `/v1/application-entry` response without adding either ID to an environment variable or application-grant table. The peer's own local account and resource policy still decides whether each can open a protected resource. Confirm stable AccessLobby person IDs and distinct peer-local account IDs.
6. **Exercise restricted entry separately.** Repeat with a second disposable `grant_required` app. Deny the ungranted person, grant their existing person ID as the owning first-party user, then verify 200 entry. Revoke and confirm the next checked protected request is denied even if a peer-local permission still exists. Check expired grants, hidden visibility, wrong owner and suspended person. An AccessLobby grant must never create a peer resource role.
7. **Check sign-out and failure.** If the backchannel endpoint was registered, choose shared sign-out and verify a signed logout event ends the matching peer session. An invalid event must not. During a simulated entry API outage, new Join and protected checks should fail closed. Record the peer's token/session expiry behavior; this reference consumer retains tokens only in memory and does not refresh them.
8. **Close or stop the pass.** From the private runner execute `node dist/suspend-app.js <app-uuid> --suspend <reference>`. It commits registry suspension first, so API client admission stops even if IAM is temporarily unavailable; it then disables the matching Keycloak client and verifies readback. If the command fails after the registry step, retry it with the same reference until IAM reads disabled. This does not revoke a peer's unchecked local sessions; the peer must recheck entry or end them itself. Remove the disposable TXT proof after suspension, retain the registry audit history, and confirm the earlier pilot remains available. Record rollback steps and outstanding failure modes. Do not treat a CI pass or public health check as signed-in acceptance.

At scale, `authenticated_open` avoids a per-customer AccessLobby grant operation. The peer's own account store and roles still need a durable design. Organization seats, delegated administrators, bulk enrollment, billing entitlements and external pairwise IDs require separate product decisions before implementation.
