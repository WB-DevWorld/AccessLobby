# ADR 010 — WordPress registration and session reconciliation

Status: **MVP-PROVISIONAL** implementation on the independent Codex comparison branch, 2026-11-23. No staging or production promotion. Extends ADR009; preserves the reviewed first-party identity contract.

**CURRENT-REPO-FACT:** the generic registry and private renderer previously rejected every URL query. WordPress core callbacks use fixed `wp-login.php?action=...` routes, and plain WordPress REST routing uses `?rest_route=...`. Runtime fixtures seeded clients directly, so they did not establish that these URLs could pass real onboarding.

**NEW-RECOMMENDATION implemented:** an additive `applications.platform` field defaults existing applications to `web`. `wordpress` permits only callback `?action=al_callback`, logout return `?action=al_signed_out` on the same exact `wp-login.php` path, and the exact plain REST backchannel query or a query-free endpoint. All routes retain HTTPS, exact registration and same-origin checks. Extra/duplicate actions, arbitrary return targets, token parameters, encoded action aliases and fragments fail. Generic web applications remain query-free. DNS proof, first-party review, private provisioning/readback and independent app admission still apply.

**CURRENT-REPO-FACT:** signed backchannel logout was implemented, but delivery to an unavailable WordPress peer could be missed. Existing alpha sessions were bounded by validated tokens and one hour; no durable continuing admission check existed.

**NEW-RECOMMENDATION implemented:** a WordPress client may request an optional opaque peer-session receipt from `/v1/me` using `x-accesslobby-session-receipt: 1`. The API stores only its SHA256 hash, bound to the already-verified issuer, client, canonical person, `sid` and expiry. Status/end calls carry the capability in an Authorization header and the registered client ID in a header. They accept no caller-supplied person/session ID. Status exposes no person, subject or `sid`.

The connector seals the receipt with its existing session association and marks the corresponding WordPress core token as SSO-created. Due checks evaluate receipt expiry, active person/client, application admission and durable shared-session revocation. Checks normally occur every 30 seconds. API failure grants at most 90 seconds since the last successful validation, then denies authenticated access without destroying a potentially recoverable cookie. Confirmed revocation destroys only that associated local token. Local/emergency sessions, Application Password authentication, cron and CLI retain their separate policy. No refresh/access token is retained by this extension or used to extend session expiry.

Before shared issuer logout, participating updated WordPress/web/reference consumers record durable revocation for their own verified browser session. The API derives `sid` from its receipt or validated bearer; a body cannot select another session. The issuer still ends browser SSO and delivers standard signed backchannel notifications. Cancellation after the marker can already have ended participating app access; it does not establish issuer SSO ended. This is not an all-devices action.

Rollout is additive: apply migrations005/006, deploy API, then plugin alpha.4. A plugin on an older API negotiates absence of receipts and preserves the earlier bounded behavior; present-but-malformed receipt data fails closed. Pre-upgrade sessions remain bounded legacy sessions until reauthentication. Connection diagnostics show receipt availability. API rollback requires retaining the additive tables and restoring the prior plugin if necessary; no person, local user or commerce rows are removed. Do not advertise the new revocation bounds for legacy sessions or unupdated consumers.

The owner's two authentication modes, explicit dual-proof links, local roles/commerce, guest policy, PWA cache rules, emergency recovery and external activation gate remain unchanged. Compatibility is qualified per source revision, not inferred from this ADR.
