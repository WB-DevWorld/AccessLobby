# ADR 011 — Closed external identity preparation

Status: **MVP-PROVISIONAL / NEW-RECOMMENDATION**, implemented preparatory storage/tests, 2026-11-23. External authentication activation remains **DEFERRED**. This does not supersede unresolved policy in `external-app-contract-decision.md`.

The current request/DNS-proof contract can now prepare an inactive external profile privately. `prepare-external-app --plan` is read-only; `--prepare REVIEW` rechecks current DNS proof, exact URLs, requested/unreviewed state and active publisher. It records an external trust classification, review reference and minimal `openid` policy. It creates no IAM client and has no IAM credential. `--suspend REVIEW` blocks the prepared profile and retains audit/consent data. The existing database constraint, first-party provisioner and API client registry still prohibit external activation, including environment-allowlist bypasses.

Additive migration007 stores random app-scoped `alx_…` identifiers with a unique `(application, canonical person)` relationship and global subject uniqueness. Consent writes use the existing first-party-authenticated canonical person, never resolve an external pairwise subject through `PostgresIdentityStore`, and never create a Person. Two unrelated apps receive distinct internal preview identifiers referring to one existing human. Email, profile, organization, local role and privileged capabilities are absent from this minimal preview.

Consent grant/withdrawal is versioned and auditable, with concurrent grants retaining one app identity. Withdrawal blocks future preview resolution; regrant retains the same app identity to avoid duplicate peer users. Publisher/person suspension also blocks resolution. Retention is deliberate pending the final policy; deletion, transfer/domain changes and person erasure are not improvised by a plugin uninstall.

The preview API is under `/v1/preview/external-consents`, requires the exact first-party web client, and is absent unless the operator explicitly sets `EXTERNAL_PROFILE_PREVIEW_ENABLED=true`. It is not enabled in Compose/staging. Requests cannot select another person. Responses contain publisher consent metadata and `activationAllowed:false`, never internal person/provider subjects or opaque subject values. There is no external sign-in button, external token endpoint, public IAM administration or automatically activated publisher.

`auditExternalPrivacy` inspects already-verified ID/access/userinfo claims jointly, compares unrelated clients' subjects/session identifiers, rejects internal identifiers/undeclared claims/scopes and first-party API audience, and emits categories only. It is not a JWT verifier. An isolated real-IAM probe obtains Code/PKCE pairwise tokens for two synthetic clients using one browser session; these clients are never admitted as external AccessLobby applications. The gate deliberately remains closed when the token contract fails. A changed `sub` alone cannot establish privacy.

**DEFERRED activation gates:** actual issuance of durable product-owned app subjects on every surface, app-scoped logout/session identifiers, separate external API audience/service, complete publisher lifecycle/transfer/recovery, consent prompt/withdrawal product UX, approved email/profile scopes and retention, independent adversarial review, and an external-like end-to-end WordPress pilot. The minimal preview makes these boundaries executable without exposing a universal identifier or creating duplicate people.

Sources: [OIDC Core §8](https://openid.net/specs/openid-connect-core-1_0.html#SubjectIDTypes), [OIDC backchannel logout](https://openid.net/specs/openid-connect-backchannel-1_0.html), [Keycloak protocol mappers](https://www.keycloak.org/admin-api/protocol-mappers). Keycloak fixture versions are pinned in CI; current mapper documentation is evidence to investigate, not proof a running version satisfies the whole external contract.
