# AccessLobby consumer contract v0.1 (MVP-PROVISIONAL)

## Discovery and client

Any compatible human-facing application can register as an OIDC client. Each environment publishes its explicit AccessLobby-controlled OIDC issuer at `OIDC_ISSUER` and its discovery at `${OIDC_ISSUER}/.well-known/openid-configuration`. Keycloak operates the issuer in MVP-0; the application integrates by protocol and AccessLobby's versioned identity API, never Keycloak's database or administration API. Consumer configuration pins the full issuer and unique client ID; redirect URIs are exact HTTPS callback URLs (localhost HTTP only for development). Use Authorization Code + PKCE S256 and `state`, with `nonce` for ID tokens. Allowed base scopes: `openid profile email`. Do not infer identity from email.

Register clients through the repeatable [consumer onboarding process](consumer-onboarding.md), adding exact redirect and logout URIs, an audience mapper for `accesslobby-api`, and an active reviewed first-party registry row, or the transitional API allowlist for existing pilot clients. Registry status takes precedence over that fallback. Do not put secrets in Git. Public clients require PKCE; confidential server clients additionally authenticate at token exchange. This v0.1 profile covers interactive human sign-in; machine, SAML and enterprise federation profiles are deferred.

## Validation and resolution

Validate signed tokens against discovery JWKS (refresh keys on rotation), `iss`, signature/algorithm, `exp`/`nbf`, intended audience and client/authorized party. The AccessLobby API accepts RS256 access tokens with `aud=accesslobby-api` and an admitted client `azp` (active first-party registry entry, or transitional allowlist when no registry row exists). `sub` is the issuer's mutable-provider boundary identifier, **not** the durable AccessLobby person ID. Never parse an unverified JWT for authorization.

Call `GET /v1/me` with `Authorization: Bearer <access token>` from the authenticated consumer backend, optional `x-request-id`. A `200` response is `{ "contract":"accesslobby.identity.v0.1", "person": {"id":"opaque UUID", "status":"active"}, "requestId":"..." }`. `401` means absent/invalid token, `403` suspended person, `503` backend unavailable. The endpoint only resolves the token's own subject. The first valid subject creates a person; subsequent calls return the same ID. A consumer stores `(issuer, sub, person.id, local user/profile id)` with an explicit auditable mapping. No automatic email linking.

Each application establishes its own secure session and performs its own app entry and resource authorization. Authentication alone never grants any application's resource access. A failed identity resolution fails new login closed; existing application sessions follow that application's documented expiry policy. During an AccessLobby outage, new login fails safely; out-of-band administrative recovery must not depend on this service.

## Join and account linking

A new user can start at the peer's Join action. The peer starts its usual OIDC code + PKCE request with `prompt=create`, preserves its return context in a short-lived server-side flow, and completes the callback only after email verification, ID/access token checks and `/v1/me` resolution. The peer creates its own local profile only after those checks; an AccessLobby identity alone never grants peer entry.

An existing user signs into the peer by its existing authentication path, chooses Connect AccessLobby, and completes a new OIDC code + PKCE flow. The peer verifies that both the original local session and the OIDC flow are still valid before atomically binding its local user ID to `(issuer, sub, person.id)`. Unique constraints prevent either side being linked to a different account; conflicts require manual recovery and an audit trail. Never merge by email. The existing user retains their peer-local history and permissions. During rollout, leave the peer's old sign-in available until its real users have a safe linking path.

## Session and logout choice

Present **This app only** and **All connected apps** at every peer's sign-out entry. The former clears only its local session and leaves the issuer session intact; the user may re-enter silently through OIDC. The latter clears that app's session and performs RP-initiated issuer logout for the current browser SSO session. Each participating server-side peer registers an exact backchannel endpoint and verifies the signed logout token's issuer, audience, signature, age, event, and session `sid` before ending matching local sessions. An invalid, replayed or unrelated logout token must never clear sessions. AccessLobby's first-party web session is capped at one hour; its API records the signed logout event and refuses later use of the revoked `sid`. An all-apps choice does **not** mean all devices.

This propagation is only effective for clients that register and run a working logout endpoint. A temporarily unavailable peer may retain a local session until its own expiry; a production peer should use short sessions and an additional issuer-session check or durable retry/revocation mechanism according to its risk. The reference consumer's in-memory session and link state is only a demonstration. Version the response compatibly; adding optional fields is nonbreaking, changing person ID meaning or token audience requires a new contract and explicit migration.

## First-party organization account extension (MVP-PROVISIONAL)

The new `GET /v1/contexts`, `POST /v1/organizations`, `GET /v1/organizations/:id`, invitation response/management and membership change routes require a valid `accesslobby-api` bearer token whose allowlisted `azp` is **`accesslobby-web`**. They resolve the human via the token and check active organization membership server-side. They are not a consumer API for peers. `/v1/me` remains exactly v0.1; no organization, role or current-context claim is added to it or to OIDC tokens.

The first-party web selector remembers a person-bound organization choice for one hour in a sealed HttpOnly cookie, then rechecks membership for display. Peers must not use that cookie or a user-supplied organization ID as proof of authority. A future versioned peer context/admission contract needs explicit owner decisions about app grants, revocation, claims and delegation. See [account actor workflows](account-types-and-workflows.md) and [ADR 006](adr/006-personal-and-organization-contexts.md).

On a successful first-party OIDC callback, the web server resolves `/v1/me` and then `/v1/contexts` before creating its local session. A person with only personal context lands on `/account`; one with active organization memberships or pending invitations lands on `/contexts` and chooses deliberately. Failure to resolve the person or contexts creates no local web session. A different human may request fresh IAM authentication with `/auth/login?intent=switch`; this is distinct from selecting an organization. The resulting first-party account view displays live memberships but does not add organization claims to OIDC tokens or grant access to a peer.

## Read-only peer membership projection (MVP-PROVISIONAL)

An allowlisted interactive client can call `GET /v1/my-organizations` with the same validated bearer token used for `/v1/me`. The API resolves that token's own active person and returns `{ "contract":"accesslobby.memberships.v0.1", "person":{"id":"same durable ID"}, "organizations":[{"id":"organization UUID","name":"self-asserted name","role":"owner|administrator|member"}], "requestId":"..." }`. Only active memberships in active organizations appear. There is no input person ID, roster, invitation or organization-management action. The first-party management routes above remain `accesslobby-web` only. `401`, `403` and `503` follow `/v1/me`; a consumer must check the contract and person ID before using the projection.

This response is for displaying and choosing a context in the consumer's own session. A consumer must recheck a selected membership before any context-sensitive operation and fail that operation closed if the membership service is unavailable or the membership ended. The response does **not** grant entry to the app, a resource role, delegation, a legal organization claim, or an entitlement. Those remain separate peer and future platform decisions. The reference app demonstrates the distinction with a peer-local protected-page grant; see [ADR 007](adr/007-peer-membership-projection.md). Its access token is retained only in server memory for membership checks, with no refresh, so context selection becomes unavailable when the token expires even if its local session has not yet expired.

## First-party application entry extension (MVP-PROVISIONAL; merged/CI-qualified, staging acceptance #44)

An approved first-party application's backend may call `GET /v1/application-entry` with the signed-in human's validated API access token. The response is `{ "contract":"accesslobby.app-entry.v0.1", "applicationId":"UUID", "clientId":"its own azp", "admitted":true, "requestId":"..." }`. The API derives the application from the token's verified `azp`; it accepts no requested application or person ID. `403 application_entry_denied` means an active restricted app lacks a current grant, and `403 application_unavailable` means no active first-party app is registered. `401` covers invalid tokens or ended sessions and `503` unavailable identity or client registry. Recheck at entry and at sensitive operations as the peer's session policy requires; an AccessLobby grant change does not magically invalidate every existing peer session. This is **broad app admission**, not a peer role or resource permission. Existing v0.1 pilot consumers are not changed until they explicitly adopt this extension.

Only the `accesslobby-web` first-party client may request an application (`POST /v1/applications`), list its owner's requests (`GET /v1/applications/mine`), verify its callback hostname (`POST /v1/applications/:id/verify-origin`), view available registered apps (`GET /v1/applications/visible`), grant a person entry (`POST /v1/applications/:id/grants` with `personId`, optional future UTC `expiresAt`) or revoke (`DELETE /v1/applications/:id/grants/:personId`). A request includes exact callback/logout URLs and optionally a same-origin backchannel logout URL whose endpoint is already implemented by the peer. It creates an inactive record with a unique DNS TXT challenge. The owner publishes the exact record shown in `/apps`, then invokes the verification route; missing proof returns 409, DNS outage 503. No public activation route exists. The private runner rechecks live DNS proof before registering the OIDC client and reads back the optional logout endpoint as well as callback, PKCE and audience. This establishes hostname control only; first-party classification still needs independent review. Grants require ownership of an active `grant_required` application and an existing active target person. Organization membership neither creates an app grant nor gives an administrator authority over a person's application request. The first-party provisioning runner and external identity/privacy contract are described in [the onboarding guide](consumer-onboarding.md).
